## 🔴 Critical Security Issues

- [x] **1. Fix CORS allowlist**
  - In `main.ts`, the CORS callback falls through to `callback(null, true)` even for unknown origins
  - Unknown/untrusted origins must be **rejected**, not accepted
  - Ensure production config is strict

- [x] **2. Bind authorization code to redirect URI**
  - Currently the auth code only stores `clientId`, not `redirectUri`
  - Store the exact `redirectUri` when the authorization code is created
  - During token exchange, validate that `redirect_uri` matches exactly
  - Important: a client can have multiple registered redirect URIs

- [x] **3. Fix OAuth error semantics**
  - Invalid / expired / already-used / mismatched auth codes must return `invalid_grant`
  - Do NOT return `401 / invalid_client` for these cases
  - `401` is for client authentication failures, not code problems

- [x] **4. Make authorization code consumption concurrency-safe**
  - Two simultaneous requests with the same code must not both succeed
  - Use CouchDB `_rev` conflict handling to ensure only one request wins
  - The losing request must NOT create a session or issue tokens
  - Add an integration/concurrency test for this behavior

- [x] **9. Replace `Math.random()` with cryptographically secure randomness**
  - OAuth `state` parameter must use `crypto.randomBytes()` (or equivalent)
  - `Math.random()` is not secure for security-sensitive values

- [x] **10. Implement proper refresh token rotation + reuse detection**
  - When a refresh token is used:
    - Validate the current token
    - Issue a new refresh token
    - Invalidate the old one
    - Store only the **hash** of the new token
  - Detect reuse of an old (already rotated) token → revoke the entire session/token family

## 🟠 Architecture Issues

- [x] **5. Keep PKCE-readiness in mind**
  - No need to implement PKCE now
  - But do NOT make design assumptions that would require a major rewrite later
  - Web/browser and mobile clients will need Authorization Code + PKCE in Phase 3

- [ ] **6. Fix OAuth 2.0 vs OIDC terminology**
  - What is currently implemented is an **OAuth 2.0 Authorization Code flow**
  - Do NOT call it a full OIDC implementation yet
  - We don't have: ID Token, UserInfo endpoint, discovery document
  - Keep it focused and label it correctly

- [ ] **7. Remove `REGISTERED_CLIENTS` from frontend**
  - File: `frontend-next/src/context/auth-context.tsx`
  - The `REGISTERED_CLIENTS` list must be removed from the frontend entirely
  - The IAM backend is the **single source of truth** for registered clients and redirect URIs
  - Frontend can know its own `client_id` (it's not a secret), but must not validate other clients
  - `callbackUrl: "/callback"` in the frontend should NOT define the OAuth redirect URI — the backend should

- [ ] **8. Stop storing tokens in localStorage**
  - Access token → **memory only** (never persisted)
  - Refresh token → **HttpOnly + Secure cookie** (web) / **platform secure storage** (mobile)
  - Remove any localStorage usage for tokens in the frontend

- [ ] **11. Revert manual edits to `next-env.d.ts`**
  - This file contains: `// NOTE: This file should not be edited`
  - It is auto-generated by Next.js
  - If changes were manually added to fix a TypeScript issue → revert and fix the root cause instead
  - If Next.js generated them automatically → confirm and document it
